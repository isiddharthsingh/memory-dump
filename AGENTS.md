# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex and others) working in this repository. `CLAUDE.md` imports this file, so edit it here.

## Repo shape

Two deployables in one repo:

- `backend/` — FastAPI + Postgres (pgvector) + Redis + arq workers. Python 3.12. Run via `docker compose` from `backend/`. `.env` lives at the repo root and is loaded by both `api` and `worker` services.
- `apps/ios/` — native SwiftUI app (iOS 26+) plus a Share Extension. Talks to the backend over HTTPS at `API_DOMAIN` from the root `.env`, compiled in at build time; the session lives in the shared Keychain.

`docs/architecture.md` is the canonical condensed design doc; the README has the smoke-test curl recipes and the API table.

## Backend — commands

All commands assume `cd backend` unless noted. `docker-compose.yml` is the stack as it runs in production (only the API's port published, no reload); `docker compose up` also merges `docker-compose.override.yml`, which publishes the databases, mounts `.` into the containers so code changes hot-reload, and builds the api image with the dev extras (pytest, ruff, mypy).

```bash
docker compose up --build              # full stack (postgres + redis + supertokens + seaweedfs + migrate + api + worker)
docker compose -f docker-compose.yml up -d --build   # production: no override
docker compose up postgres redis supertokens seaweedfs   # infra only, then run api/worker on host
                                       # with SUPERTOKENS_CONNECTION_URI=http://localhost:3567
                                       # and S3_ENDPOINT_URL=http://localhost:8333

docker compose exec api alembic upgrade head            # migrations (the one-off `migrate` service runs them before api and worker start)
docker compose exec api alembic revision -m "msg" --autogenerate

docker compose exec api pytest                          # all tests
docker compose exec api pytest tests/test_ask.py        # single file
docker compose exec api pytest tests/test_ask.py::test_name -x

docker compose exec api ruff check .                    # lint
docker compose exec api ruff format .
docker compose exec api mypy app                        # type-check
```

Worker entry point: `arq app.workers.worker.WorkerSettings` (the `worker` compose service runs this). Functions registered there: `ingest_item`, `ingest_file`, `synthesize_topics`, `forget_item`, `compact_topics`, `compact_user`, `weekly_digest`, `digest_user`. Cron jobs: `compact_topics` nightly at 03:14 UTC and `weekly_digest` on Sundays at 16:00 UTC (each only queues one job per user), `requeue_stuck` every 5 minutes and at startup, `sweep_files` hourly, `observe_queue` every minute.

`SUPERTOKENS_API_KEY` reaches the core (as `API_KEYS`), `migrate`, `api` and `worker` from one place, your shell or `backend/.env` (compose interpolation, where the shell wins), so they can't disagree; the core takes only letters, digits, `=` and `-` in it. `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` reach SeaweedFS (as its admin `AWS_*` pair), `api` and `worker` the same way, and compose won't start without them.

`pytest-asyncio` is in `asyncio_mode = "auto"` — don't decorate async tests with `@pytest.mark.asyncio`.

## iOS — commands

```bash
cd apps/ios
xcodegen                                                # project.yml → MemoryDump.xcodeproj (gitignored)
open MemoryDump.xcodeproj                               # set your team under Signing, run on a device

# simulator build and tests (pass -parallel-testing-enabled NO, or xcodebuild clones simulators and stalls)
xcodebuild -project MemoryDump.xcodeproj -scheme MemoryDump -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
xcodebuild test -project MemoryDump.xcodeproj -scheme MemoryDump -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -parallel-testing-enabled NO
```

`project.yml` is the source of truth for targets, entitlements and Info.plist keys; edit it and re-run `xcodegen` instead of changing the generated project in Xcode. `DEVELOPMENT_TEAM` is the free Personal Team (`L53NYQQX76`) until a paid account exists: device installs expire after 7 days, and the app's `aps-environment` entitlement is left out because Personal Teams can't sign push. With a paid team, change the ID and add `aps-environment: development` back under the app target's entitlements.

Three targets: `MemoryDump` (app), `ShareExtension`, `MemoryDumpTests` (Swift Testing). `Shared/` is compiled into both the app and the extension: the API client, models, Keychain session store and the offline share queue. The two processes share state through App Group `group.com.siddharthsingh.memorydump` (queue files, lock file) and a Keychain access group (session).

The server address is not entered in the app. A `Server address` pre-build script in both the app and extension targets reads `API_DOMAIN` from the repo-root `.env` the way python-dotenv does (`export`, quotes, trailing `# comment`) and writes `Server.url` to `Generated/<target>/Server.swift` (gitignored, an optional source of each target; Xcode doesn't compile Swift a script writes to DerivedSources). With no `.env` or no `API_DOMAIN` it warns and uses the backend's default, `http://localhost:8000`, which only the simulator reaches: a build for a phone stops with an error instead. A phone on the Mac's Wi-Fi needs `http://<mac>.local:8000`; a deployed server needs https, and plain http to a public host warns because App Transport Security blocks it. Changing `.env` rebuilds with the new address; no `xcodegen` needed.

## Architecture — the parts that span multiple files

### Ingest pipeline (per-item, async)

`POST /ingest` (`app/api/ingest.py`) inserts an `Item` row with `status="pending"` and enqueues `ingest_item` on arq. `(user_id, url)` is unique, so sharing a saved URL again returns the saved item, re-queued if it had failed; uploads get a `file://<item id>/<filename>` placeholder URL so files with the same name stay separate. `POST /ingest/file` streams the upload, at most 5 MB, into upload storage (`app/storage.py`: with `STORAGE_BACKEND=s3`, an S3-compatible bucket, by default the compose stack's SeaweedFS, which the API reaches on the compose network only; or the shared `uploads` volume) before the row is written, records its `upload_key`, and takes an `Idempotency-Key` header (the app sends its queue entry's id), unique per user, so a resend after a timeout returns the first item. The worker in `app/workers/ingest.py` runs the full pipeline:

1. `app/extractors/` — per-source extractor selected by `get_extractor(source)`. `source` is detected from the URL (`youtube` / `twitter` / `instagram` / `webpage`). Posts on X come from the FxTwitter API (`api.fxtwitter.com`, the open-source FxEmbed project, no auth), which has the full text of long posts, quoted posts and X Article bodies, with X's oEmbed as the fallback; a post that links out also gets the linked page through that page's own extractor. Anyone who can sign up picks the URLs the server fetches, so every extractor fetches through `public_client()` (`app/extractors/webpage.py`): its `PublicOnlyTransport` resolves and checks the address as each connection opens, redirects and changed DNS answers included, and refuses anything that isn't public (this machine, the compose network, private ranges, `.local` names, cloud metadata) with `NotPublic`, which the app shows as "This link points to a private network". A consequence: pages on your own network (a NAS, `http://<mac>.local`) can't be saved. YouTube metadata goes through yt-dlp instead, which only ever talks to YouTube. So does an Instagram post with a video, through yt-dlp's Instagram extractor only (`app/extractors/reel.py`): a child process (`python -m app.extractors.reel`), limited to 2 GB of address space, given none of the worker's environment, run as a sandbox user of its own and killed, with the ffmpeg it starts, after two thirds of `EXTRACT_TIMEOUT_S` (the rest is for the post's page; the worker's `init: true` reaps what a kill leaves), downloads the smallest video stream, takes 8 frames evenly through it and transcribes the first 5 minutes with faster-whisper (`base`, which the Dockerfile puts in the image under `HF_HOME`; change `WHISPER_MODEL` and that download together). It writes the frames before the transcript, so a reel that runs out of time keeps its caption and frames. The analysis sees the frames and returns the text on them as `on_screen`, which the worker saves as the item's `On screen:` section. A photo, or a video Instagram won't hand over (it often wants a login from data-centre addresses), is read from the post's page as before. Build any new extractor's client with `public_client()`. Extractors return `Key: value` sections separated by blank lines, which the app's reader parses, so no section value may contain a blank line. HTML is parsed with `selectolax.lexbor` (selectolax 1.0 removed the `selectolax.parser` backend).
2. `app/ai/analyze.py` — Claude (`CLAUDE_ANALYSIS_MODEL`, Haiku by default) returns title, summary, tags, and the **lexical anchors**: `people`, `handles`, `brands_products`, `topics`. These anchors are persisted as Postgres `ARRAY(Text)` columns AND folded into the text that gets embedded — they're what makes proper-noun queries work.
3. `app/ai/embed.py` — `chunk_text` + Voyage `voyage-3-large` (1024-dim) into `item_chunks.embedding`. Re-ingest is idempotent: existing chunks for the item are deleted before insert.
4. Status transitions: `pending → processing → ready` (or `failed` with `error` text). `POST /items/{id}/retry` re-enqueues. Every enqueue (save, re-share of a failed item, retry, an edited note) bumps `items.ingest_generation` and queues the job for that generation under the job id `ingest:<id>:<generation>`. A job claims the item only while its generation is current, and saves under the item's row lock only if it still is, so a job overtaken by a newer request writes nothing and two runs never interleave chunks (`(item_id, ord)` is unique).
5. On success, the worker enqueues `synthesize_topics` for that item via the shared arq Redis (`ctx["redis"].enqueue_job(...)`).

An upload (`ingest_file`) skips the extractor: the vision provider returns the analysis and the text in one call. Its file is kept, moving from `upload_key` to `file_key`, beside a JPEG thumbnail at most 1200 px on its long side (`app/thumbnails.py`: the image scaled down with Pillow, or the top of a PDF's first page drawn by PDFium; a file it can't draw just gets none). Each is drawn in a child process (`python -m app.thumbnails`) limited to 1 GB of address space, killed after 30 s and given none of the worker's environment (its keys), and an image over 50 megapixels isn't decoded, so a file built to exhaust memory or render forever costs only that process. Both this child and the reel child run as an unprivileged user of their own, one of `sandbox0`–`sandbox7` (uids 61000–61007, away from the 999 Postgres and Redis run as) that the Dockerfile creates, capped at 512 processes. `sandbox.user()` in `app/sandbox.py` takes a user by locking a root-only file in `/run/memory-dump-sandbox`, so no two children in the container share one, a script run beside the worker included, and kills everything running as the user before handing it out and when its child is done; a user whose processes outlive that stays locked until the worker restarts. So one taken over through a decoder bug can't read the worker's environment from `/proc` or the secrets, reach another child working on someone else's save, lift its own limits, or linger for the next. The worker keeps only a bounded JPEG from this one and only what a reel could hold from the other (`reel.read`). The image copies only what `.dockerignore` lets through (no `.env`, keys or caches), and only `app/` is readable to them. They can still reach the compose network, so give Redis a password in production. `thumbnail_url` holds `/items/<id>/thumbnail`, a path the API serves only to the item's owner. A file that fails for good is deleted with its thumbnail; deleting the item deletes both. Every stored key starts with its item's id, so the hourly `sweep_files` job deletes any file over an hour old whose item is gone (an upload whose row never landed, a deleted account's files, a delete that couldn't reach storage): keep nothing else in the bucket.

If you add a new source type, the work is: new extractor in `app/extractors/`, register it in `get_extractor`, and make sure the URL→source detector in the ingest API recognizes it.

### Wiki synthesis (Karpathy LLM-wiki pattern)

`app/workers/synthesize.py` + `app/ai/synthesize.py`. After each successful ingest, Claude (`CLAUDE_SYNTHESIS_MODEL`, Sonnet) **patches** existing `topic_pages` rather than regenerating them. Pages are markdown with `[[wikilinks]]`; `backlinks` and `source_item_ids` are tracked on the row, `version` increments per patch. `topic_page_chunks` mirrors `item_chunks` so wiki content participates in the same retrieval fusion.

No writer holds a transaction across a Claude call. Synthesis drafts each page from a copy read without a lock, then writes all its drafts in one short transaction under the per-user wiki lock (`lock_wiki`), only if no page's `version` changed meanwhile; a page that did is drafted again on the new copy (up to 3 rounds, then the job runs again later). A failed try writes nothing. `items.wiki_status` goes `pending` (ingest done) → `done`, or `failed` when synthesis gave up.

`compact_topics` (nightly) queues one `compact_user` job per user, the GC pass: it queues `forget_item` again for items the user's pages still cite that no longer exist, then merges near-duplicate pages Claude proposes, each written under the lock only if none of its pages changed since.

Deleting an item leaves no trace of it. `DELETE /items/{id}` enqueues `forget_item` (also in `app/workers/synthesize.py`) before it deletes, so a delete never lands without its cleanup; the job retries until the item is gone. Pages only that item supported are deleted at once, along with the Ask history source cards and `[item:…]` / `[wiki:…]` markers that point at the item or those pages (a chat's `updated_at` is left alone, so History keeps its order). Then each page that cites the item or links to a deleted page is rewritten in its own transaction: Claude (`CLAUDE_SYNTHESIS_MODEL`, `FORGET_SYSTEM`) rewrites it, `forget_in_body` removes whatever is still cited only to the item and unlinks links to deleted pages, and the page is re-embedded with its `version` bumped. Last, stub pages nothing links to any more are deleted. Rate limits and overloads retry with backoff like ingest, and a retry picks up the pages still left. Synthesis and `forget_item` both take a per-user Postgres advisory lock (`_lock_wiki`), so neither writes a page from a copy the other has changed; a job that waits 30 s for it runs again later instead of holding a worker. Synthesis keeps nothing when its item was deleted while Claude was writing.

### Hybrid retrieval (`/search` and `/ask`)

`app/ai/retrieval.py` is the single source of truth and is used by both endpoints. The pipeline:

1. **Dense**: pgvector HNSW over `item_chunks.embedding` ∪ `topic_page_chunks.embedding`, query embedded with Voyage `input_type="query"` (cached in Redis for a day). The indexes hold every user's chunks and the user filter applies after them, so the query turns on pgvector 0.8's iterative scan (`hnsw.iterative_scan = relaxed_order`) to keep scanning until it has this user's nearest chunks. When the query can't be embedded, search goes on with keywords only.
2. **BM25**: Postgres `tsvector` full-text over the same two tables: the stored `fts` column on each chunk and the item's or page's `fts_doc`, each with a GIN index. The GIN index on the lexical-anchor arrays is what gives proper-noun queries deterministic recall. After these two queries `hybrid_search` commits, so no pooled connection is held while Voyage reranks and Claude answers.
3. **Reciprocal Rank Fusion** merges the two ranked lists.
4. **Voyage `rerank-2.5`** reorders the top candidates.
5. `/ask` (`app/ai/ask.py`) feeds the reranked context to Claude (`CLAUDE_ASK_MODEL`, Opus) which must cite as `[item:UUID]` / `[wiki:slug]`. `/search` returns the hits directly, minus chunks found only by the dense search whose rerank score is under `_MIN_SCORE` (`app/api/search.py`): nearest neighbours exist even for a query that matches nothing.

If you change the chunking or embedding model, both `items` and `topic_pages` need re-embedding, and `EMBED_DIM` in `app/db/models.py` plus the migration's `Vector(N)` must match.

### Ask history (`/chats`)

`app/api/chats.py`: each `chats` row holds one conversation's turns as JSONB, under an id the app picks. The app PUTs the whole chat when a question is asked and again when the answer finishes; `GET /chats` returns only each chat's questions for History, a page at a time (`before=<last chat id>`), and `GET /chats/{id}` the full turns. Each save bumps `chats.version`; a PUT that names the version it was built on (0 for a new chat) gets 409 when another device saved in between, and the app merges by turn id and saves again (`Chat.merge`). A PUT without a version always wins. Turn JSON uses single-word keys (`status`, `error: {title, detail}`) because the app encodes request bodies with a plain `JSONEncoder`, without snake_case conversion. On iOS, `AskModel` sends every chat write through one serial queue, so an older copy never lands after a newer one or after a delete.

### Share queue (iOS)

`Shared/ShareQueue.swift`. The share extension writes every share to the queue in the App Group before it sends anything, then tries once with a 10-second timeout (`APIClient.shareTimeout`, for `/ingest` and between bytes of `/ingest/file`), so a server that never answers, or closing the pill, can't lose a share. `ShareQueue.send` holds a per-entry `flock()` (`<id>.lock`) so the app and the extension never send one entry at once, and removes it once it is sent or refused with a 4xx; on no answer, cancellation, 408, 429, 5xx or a signed-out session it stays (`waits(after:)`). `flush` stops only when every share would wait (`holdsUpQueue`: unreachable, rate-limited, signed out); one that 500s is skipped, not left blocking the rest. While the app is in front and signed in, `AppModel.sendQueue` sends what's left, then again after 5, 10 and 20 s and every 30 s, and at once when the network changes (`NWPathMonitor`). A send under way is never cancelled for a retry or for going to the background, since the server may already have it. The Library shows the waiting shares at the top (`QueuedShares`).

### Offline copy (iOS)

The app stays readable with no server. `APIClient` saves every GET body to disk per account (`Shared/SavedResponses.swift`, Application Support/Offline/<user id>/, keyed by path and sorted query), and when a request can't reach the server (any `URLError` but cancel, or 502/503/504) a GET returns that saved copy and sets `isOffline`, which the Library and Wiki subtitles show. Writes never fall back. `APIClient.saved` reads only the saved copies, so screens show them at once and then refresh from the server. `MemoryDump/App/OfflineSync.swift` runs when the app becomes active: it walks `/items` in the Library's page size (so offline scrolling finds the same pages), then fetches each item, wiki page and chat whose status, version or `updated_at` changed since its last walk. Items and chats the server no longer lists lose their saved copies too, and so do wiki pages once they answer 404 (the list holds only the 100 most recently updated). Thumbnails go through `CachedImage`, a disk `URLCache` that always prefers its copy; an upload's, a `thumbnail_url` that is a path, is fetched through `APIClient.thumbnail` with the session's token and stored by hand, so an error response is never kept. Signing out, deleting the account, or a rejected session clears both. Search and Ask still need the server.

### Auth

SuperTokens (self-hosted core, `supertokens-python` SDK) owns accounts, passwords and sessions. The core is the `supertokens` compose service, keeping its tables in the `supertokens` schema of the same database; `app/auth/supertokens.py` initialises the SDK with the Session, EmailPassword and Dashboard recipes, and `app.main` adds its middleware. SuperTokens serves its own routes under `/auth` (`signup`, `signin`, `signout`, `session/refresh`, and the user dashboard at `/auth/dashboard`); `GET`/`DELETE /auth/me` in `app/api/auth.py` sit beside them. The app uses header-based sessions: it sends `st-auth-mode: header`, reads the `st-access-token` and `st-refresh-token` response headers, and sends `Authorization: Bearer`. Access tokens last 15 minutes and refresh tokens expire after 30 days unused (`ACCESS_TOKEN_VALIDITY` / `REFRESH_TOKEN_VALIDITY` on the core service), and the core hashes passwords with Argon2id (`PASSWORD_HASHING_ALG`). The core's `API_KEYS` must match `SUPERTOKENS_API_KEY`. Passwords must be 10 to 100 characters (`_validate_password`); with `ALLOW_SIGNUP=false` sign-up answers a `GENERAL_ERROR` the app shows as is.

The app's `users` table holds only `id` (the SuperTokens user ID), `display_name` and `created_at`; the email and password live in SuperTokens. The EmailPassword `sign_up` override creates the `users` row for every new login, including ones made from the dashboard, and the optional `name` sign-up field becomes `display_name`. Migration `0006_supertokens` imported the pre-SuperTokens accounts into the core with their Argon2 hashes and their old ids as external user IDs, so it needs the core running.

Owner-scoped routes depend on `app/deps.py:get_current_user`, which runs SuperTokens' `verify_session()` and loads the `users` row, and filter by `user_id`, so no user sees another's items, wiki, chats or devices (`tests/test_ownership.py`, `tests/test_chats.py`). `DELETE /auth/me` deletes the row, relying on `ON DELETE CASCADE` foreign keys to remove everything the user owns, then deletes the SuperTokens user and its sessions. Deleting a user from the dashboard removes only the login; the library stays until the row is deleted. `/ingest` (with `PATCH /items/{id}` and `/items/{id}/retry`, which re-run the pipeline), `/ask` and `/search` are rate-limited per user, and `/auth/signin` and `/auth/signup` per client address, by token buckets in Redis (`app/auth/rate_limit.py`); a 429 carries `Retry-After`. When Redis can't be reached, requests go through.

SuperTokens rotates refresh tokens, and a refresh token used again after its replacement has been used ends the session (theft detection). On iOS the session is stored in the shared Keychain (`apps/ios/Shared/SessionStore.swift`) and attached by `apps/ios/Shared/APIClient.swift`, which refreshes once after a 401; `AuthAPI` there speaks SuperTokens' header-based protocol directly. The official SuperTokens iOS SDK isn't used: its URL protocol buffers whole responses and drops upload bodies, which would break `/ask/stream` and file uploads. The app and the share extension can both refresh, so `SessionStore.refresh` holds a `flock()` on a file in the App Group and re-reads the Keychain after taking it. Keep that lock if you touch refresh.

### Push

`app/notifications.py` sends straight to APNs over HTTP/2 with a token-based `.p8` key (`APNS_KEY_PATH`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_TOPIC` in `.env`; the worker mounts `secrets/` at `/run/secrets`; keep the key at mode 600 so the sandbox users can't read it). With no key path, pushes are skipped. The iOS app can't receive them until it is signed by a paid team with the `aps-environment` entitlement (see iOS — commands). Each `devices` row stores the hex token and `apns_env` (`sandbox` for Xcode builds, `production` for TestFlight/App Store), which picks the APNs host. Tokens APNs reports as gone (410 / BadDeviceToken) are deleted.

### Reliability: what puts work back and what stops runaway load

- **Lost jobs** (`app/workers/reconcile.py`, every 5 minutes): the API commits an item and then queues its job, and Redis keeps the queue in an append-only file synced every second, so a crash or restart can still lose one. `requeue_stuck` queues again pending items untouched for 10 minutes and ready items whose `wiki_status` is still `pending` after 30; their job ids make arq refuse any that still exist. Items `processing` past `JOB_TIMEOUT_S` + 5 minutes turn `failed`, and tombstones older than `TOMBSTONE_DAYS` go. Hourly, `sweep_files` deletes stored files whose item is gone.
- **Retries**: transient failures (a provider's 429/5xx/529, timeouts, connection errors; a site's 5xx or timeout; upload storage unreachable or answering 5xx) retry with exponential backoff with jitter, or after the provider's Retry-After; provider failures get 8 tries, site failures 3. Anything else fails at once.
- **Providers** (`app/ai/clients.py`): one client per process; calls in flight per provider are capped across all processes by a Redis lease set (`ANTHROPIC_MAX_CONCURRENCY`, `VOYAGE_MAX_CONCURRENCY`), of which jobs may hold three quarters, so Ask and Search always find one; after 5 transient failures in a row a process stops calling that provider for 30 s (`ProviderUnavailable`, which the API answers with 503 and Retry-After). Ask has its own timeout (`ASK_TIMEOUT_S`). Tokens are counted per user, day and model in `llm_usage` (`app/usage.py`) and in Prometheus.
- **Timeouts and caps**: Postgres ends statements after `DB_STATEMENT_TIMEOUT_MS` and idle transactions after `DB_IDLE_IN_TRANSACTION_TIMEOUT_MS`; `get_current_user` commits after loading the user so a request holds no connection while it waits on Claude. Link extraction gets `EXTRACT_TIMEOUT_S` and reads at most `EXTRACT_MAX_BYTES` of a page, counted after decompression (`TooLarge`). Request bodies are capped (`BodyLimit` in `app/observability.py`: 10 MB, uploads 6 MB) before Starlette reads them, and an uploaded file over 5 MB (`MAX_UPLOAD_BYTES`) gets a 413 before it is stored; the share extension refuses one first (`ShareQueue.maxFileBytes`).
- **Sync** (`app/api/items.py`): `GET /items` pages by `before=<last item id>` on `(created_at, id)`, which a deleted cursor item survives through its tombstone. `GET /items/changes?since=<until>` lists ids changed and deleted since a previous call, so the app's offline sync refreshes only those. Item, wiki page and chat detail GETs carry an ETag and answer `If-None-Match` with 304.
- **Health and metrics**: `/livez` (the process answers), `/readyz` (Postgres and Redis answer within 2 s; the compose healthcheck), `/metrics` for Prometheus (only with `Authorization: Bearer $METRICS_TOKEN`; the worker serves its own on `WORKER_METRICS_PORT`, including queue depth and the oldest job's wait). The worker's healthcheck is `arq --check`. Errors go to Sentry when `SENTRY_DSN` is set.

### DB & migrations

SQLAlchemy 2.x async (`asyncpg`) for app code; Alembic uses the sync `psycopg` URL (see `Settings.sync_database_url`). The schema lives in `app/db/models.py` and the initial migration `backend/alembic/versions/0001_initial.py` — that file also creates the pgvector HNSW indexes, the GIN FTS indexes, and the immutable `tsvector` generated columns. Don't autogenerate over the FTS bits blindly; they were hand-tuned (see commit `7d70d17` for the immutability fix).

### Models / providers — where they're set

All Claude/Voyage model IDs are env-overridable in `app/config.py` (`CLAUDE_ANALYSIS_MODEL`, `CLAUDE_SYNTHESIS_MODEL`, `CLAUDE_ASK_MODEL`, `VOYAGE_EMBED_MODEL`, `VOYAGE_RERANK_MODEL`). Defaults are in `.env.example`. Don't hardcode model IDs at call sites — pull them from `get_settings()`.

## Conventions specific to this repo

- Backend lint: `ruff` with `select = ["E", "F", "I", "B", "UP", "SIM", "ASYNC"]`, line length 100, `E501` ignored. Target `py312` syntax (use `X | Y` unions, `list[...]`, `from __future__ import annotations` where helpful).
- iOS response types are `Codable` structs in `apps/ios/Shared/Models.swift`, decoded with `convertFromSnakeCase` — when adding/changing a backend response shape, update the struct or decoding will fail in the app.
- iOS navigation: three tabs (Library, Wiki, Ask), each a `NavigationStack` whose path lives in `Router`; `Route.item` / `Route.wiki` are the detail screens. In-app links use `memorydump://wiki/<slug>` and `memorydump://cite/item:<id>`; `LinkRewriter` turns `[[slug]]` and `[item:<id>]` tokens into them and `Router.open` handles them.
- iOS colors come from `Palette` and `Swatch` in `Design/Theme.swift`, each with a light and a dark value; don't hardcode `.white` or `.black` for anything that sits on the page. Text on an ink, accent or failed fill uses `Palette.onInk`, titles on a topic pastel use `Palette.onPastel`, and shadows use `Palette.shadow(_:)`. The Settings › Appearance choice (`Appearance`, in UserDefaults) sets the window's interface style, so sheets and alerts follow it.
- Swift 6 with main-actor default isolation. Closures handed to system APIs that call back on other queues (NSItemProvider, AVAudioEngine, Speech) must be `@Sendable` or built in a `nonisolated` function, or they trap at runtime.
- Logs are JSON lines through structlog (`app/logging_setup.py`; `LOG_FORMAT=console` for a terminal), stdlib `logging` included, each carrying the request id, job, user and item from structlog's context vars. Don't add `print()` in worker or API code.
- Every call to Claude or Voyage goes through `app/ai/clients.py` (`claude`, `claude_stream`, `voyage_embed`, `voyage_rerank`), never a client of its own: that's where the per-provider concurrency cap, the circuit breaker, timeouts and token-usage recording live.
- Jobs are decorated with `@job` (`app/workers/jobs.py`) and meet a transient failure (`app/errors.is_transient`) with `raise later(ctx, ...)`, but check `last_try(ctx, exc)` first and record the failure (the item's `status`, its `wiki_status`) instead: arq drops a job past `MAX_TRIES` without running it. Queue jobs with `app.queue.enqueue` (it carries the request id), with a `_job_id` whenever queueing the same work twice must not run it twice.
- Routes are served under `/v1` and, for builds from before it, unversioned (`app/main.py`); the app calls `/v1` (`APIClient.route`) and sends `X-App-Build`, and `MIN_APP_BUILD` turns older builds away with 426.
